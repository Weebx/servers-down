# Запасной ярус: GitHub Pages (если умер весь сервер)

`pages/index.html` — копия заглушки для **крайнего случая**: случилось то, от чего
не защищает даже прокси-заглушка в Coolify — VPS мёртв целиком (не отвечает и прокси,
`502` некому отдавать). GitHub Pages живёт на серверах GitHub и переживает смерть
всего твоего сервера.

⚠️ Прокси-заглушка (`fallback-page/`, nginx-контейнер) — **ярус 1**, работает сама.
Pages — **ярус 2**, включается вручную (DNS-переключение), потому что GitHub не может
сам перехватить трафик: пока DNS смотрит на VPS, до Pages никто не дойдёт.

## Как это устроено

Pages-копия отличается от основной страницы осознанно (генерируется скриптом
`build-pages.cjs` из `../html/maintenance.html`):

| Что | Почему |
| --- | --- |
| Относительные пути (`fonts/…`, `assets/…`) | Pages живёт в подкаталоге `/servers-down/` — абсолютные пути сломались бы |
| Автопробки **нет** | DNS уже смотрит на GitHub; автопроверка зациклила бы саму страницу |
| Кнопка «Открыть сайт» вместо «Проверить снова» | заработает, когда вернёшь DNS на VPS |
| Панель: «SERVER DOWN · весь сервер лежит» | честный статус для зрителей |
| Плашка в шапке «Disaster mode · Pages» | видно, что включён аварийный ярус |

## 1. Разовая подготовка (сделай заранее, пока всё работает)

1. Репозиторий уже создан: **`Weebx/servers-down`** (project page). Адрес Pages:
   `https://weebx.github.io/servers-down/` — org site host обязан совпадать с
   именем организации (Weebx), поэтому URL именно такой, с хвостом по имени репо.
2. Залей содержимое этой папки **как есть** на ветку `main`:
   ```
   index.html
   fonts/          (4 файла .woff2)
   assets/maintenance-girl.png
   ```
   Через веб-UI: Add file → Upload files (папки создаёт drag&drop), надёжнее — `git push`.
3. Settings → Pages → Source: `Deploy from a branch` → `main` / `/ (root)` → Save.
4. Проверь: `https://weebx.github.io/servers-down/` открывает заглушку (шрифты и арт загрузились).
5. Settings → Pages → Custom domain: `weeb-x.com` → Save — **или сделай это один раз
   через `gh api -X PUT repos/Weebx/servers-down/pages -f cname="weeb-x.com" ...`**
   (как уже сделано). Домен сохранится со статусом «не проверен» — это норма:
   пока DNS смотрит на VPS, GitHub не может его верифицировать. Проверка и
   сертификат Let's Encrypt заработают сами в момент аварии, когда DNS
   переключат на GitHub (§2). **Enforce HTTPS не включай заранее** — без
   сертификата он положит сайт; GitHub сам включит проверку, когда выдастся
   LE-сертификат.

> С этого момента: при настроенном custom domain адрес `weebx.github.io/servers-down/`
> отдаёт 301 на `weeb-x.com` — это стандартное поведение GitHub, не баг. Содержимое
> Pages-репо проверяй по raw-файлам (`raw.githubusercontent.com/Weebx/servers-down/main/...`),
> а живая проверка заглушки возможна только при DNS-переключении (§2).

Готово: лазейка ждёт, ничего больше не трогай — Pages-страница просто лежит там.

## 2. Действия при катастрофе (VPS умер целиком)

1. **Cloudflare → DNS → запиши, что удаляешь** (чтобы вернуть один в один).
2. Удали у `@` (и `www`, если есть) записи A/AAAA, указывающие на IP VPS.
3. Добавь: `CNAME @ → weebx.github.io` (рекомендую **DNS-only/серое облако**) —
   Cloudflare сам сплющит CNAME на apex, GitHub это устраивает.
4. Подожди резолва (обычно минуты). Открой `https://weeb-x.com` — заглушка, но уже
   с GitHub. Зрители видят брендированную страницу и ссылку на TG.
5. Напиши в TG-канал/чат сам — кнопка есть, но живое сообщение лучше.

### Что именно нажимать в Cloudflare (аккаунт есть — быстрый путь)

Состояние зоны на 2026-10-21: аккаунт есть, зона активна (`conrad`/`aurora`), прокси
выключен — все записи «серые». **Это правильное состояние**, менять его не надо:
Cloudflare работает просто как DNS, а прокси нам не нужен (с оранжевым облаком
GitHub не выпустит сертификат и пойдут петли редиректов).

Cloudflare → выбери `weeb-x.com` → **DNS → Records**:

1. Сделай скриншот списка (rollback: `A @ → 109.68.171.140`).
2. **Delete** запись `A` с именем `weeb-x.com` (`@`) и содержимым `109.68.171.140`.
   Записи `A api`, `A dev`, `A mail` — **не трогай**, они не влияют на сайт.
3. **Add record**: Type `CNAME`, Name `@`, Target `weebx.github.io`,
   Proxy status **DNS only** (серое облако), TTL `Auto` → Save.
4. `www` уже `CNAME → weeb-x.com` — он поедет следом сам.
5. MX (`mx1`/`mx2.beget.com`) и TXT-верификации не трогай — почта и подтверждения
   в поисковиках останутся.

Итог должен стать таким (проверка через минуту):

```bash
dig +short weeb-x.com          # 185.199.108.153 … .111.153
dig +short www.weeb-x.com      # те же четыре адреса
curl -sI https://weeb-x.com | head -3   # HTTP/2 200, server: GitHub.com
```

Важно про «отключено»: **`Pause Cloudflare` и отключение DNSSEC ни на что не влияют**
— записи раздаются в любом случае. Влияет только `Proxy status` (должен быть серым) и
сама запись `@`. И не переключай NS у регистратора, пока Cloudflare доступен: правка
одной записи применяется за TTL 300 с, а смена NS — до нескольких часов.

Откат после восстановления VPS: удалить `CNAME @` → `weebx.github.io` и вернуть
`A @ → 109.68.171.140` (серое облако).

### Если заглушка «не работает»

Почти всегда это значит, что **DNS всё ещё смотрит на VPS**: страница на Pages
уже собрана, но запросы до GitHub просто не доходят. Проверка в три команды:

```bash
dig +short weeb-x.com      # 185.199.108-111.153 = GitHub Pages; 109.68.171.140 = старый VPS
dig +short www.weeb-x.com  # должен резолвиться в те же адреса (через CNAME на apex)
dig +short NS weeb-x.com   # conrad.ns.cloudflare.com / aurora.ns.cloudflare.com
```

Сторона GitHub:

```bash
gh api repos/Weebx/servers-down/pages      # "status": "built", "cname": "weeb-x.com"
gh api repos/Weebx/servers-down/pages/builds/latest   # последний билд без error
```

Если `status: built`, `cname` верный, а `dig` отдаёт IP VPS — чинится только
переключением DNS (§2). Ждать «пока само» бессмысленно: GitHub не может
перехватить трафик, пока запись указывает на твой сервер.

### Проверка, что переключение сработало

```bash
dig +short weeb-x.com     # 185.199.108.153 / .109.153 / .110.153 / .111.153
curl -sI https://weeb-x.com | head -3   # HTTP/2 200 + server: GitHub.com
```

`server: GitHub.com` в заголовках — верный признак, что отдаёт Pages, а не VPS.
После этого обнови страницу с очисткой кэша (или проверь в приватном окне):
DNS в Cloudflare кэшируется на TTL записи (300 с), браузер — отдельно.

### Если HTTPS не открывается

Сертификат Let's Encrypt GitHub выпускает сам, но только после того, как DNS уже
смотрит на GitHub: обычно 5–30 минут, максимум сутки. Пока сертификата нет,
`https://` ругается, а `http://` работает — это нормальный промежуточный этап.

1. **Не включай «Enforce HTTPS», пока сертификат не появился** — иначе сайт ляжет.
2. Если через час сертификата всё ещё нет: Settings → Pages → Custom domain →
   удалить `weeb-x.com` → Save → вписать заново → Save (перезапускает выпуск).
3. Прокси Cloudflare (оранжевое облако) для `@` держи **выключенным**: с ним
   GitHub видит не тот Host, и начинаются петли редиректов / `526`.

Проверка, что сертификат готов (появилось поле `https_certificate` — выпустился):

```bash
gh api repos/Weebx/servers-down/pages \
  --jq '{https_enforced, cert: .https_certificate.state, domains: .https_certificate.domains}'
```

Пока сертификата нет, поля `cert`/`domains` будут `null`, но страница уже открывается
по `http://`. Когда браузер показывает замок на `https://weeb-x.com` — заходи в
Settings → Pages и поставь галочку **Enforce HTTPS**, чтобы http больше не работал.

Чек-лист «почему сертификат не выпускается» (проверено 2026-10-21 — всё чисто):

- `CAA` на домене отсутствует → LE не заблокирован.
- `AAAA` у `www` указывает на GitHub (`2606:50c0:8000::153`…), а не на VPS.
- хвостов `TXT _acme-challenge` нет.
- прокси Cloudflare выключен, `pending_domain_unverified_at` = `null` (домен подтверждён).

### Если доступа к аккаунту Cloudflare нет

Важно: зона `weeb-x.com` **делегирована на Cloudflare** независимо от того, есть у тебя
там аккаунт или нет — SOA домена `aurora.ns.cloudflare.com`, NS `conrad` + `aurora`.
Кто-то (прошлый разработчик или ты сам раньше) завёл домен в Cloudflare. Пока NS
смотрят туда, менять записи можно только в том аккаунте.

Фактическое состояние зоны (проверено 2026-10-21):

| Запись | Значение |
| --- | --- |
| `A @`, `A api`, `A dev`, `A mail` | `109.68.171.140` — твой VPS |
| `CNAME www` | `weeb-x.com` |
| `MX` | `10 mx1.beget.com`, `20 mx2.beget.com` — почта на Beget |
| `TXT @` | google-site-verification, yandex-verification, pinterest-site-verification |
| `TXT _dmarc` | `v=DMARC1; p=none` |
| `CAA` | отсутствует — LE-сертификат GitHub выпустит без ограничений |

Если аккаунт Cloudflare не найдёшь, DNS переключается **у регистратора** (одноразово,
дальше всё живёт без Cloudflare):

1. Панель регистратора (почта на `mx1.beget.com` → скорее всего Beget) → Домены →
   `weeb-x.com` → DNS-серверы → переключить на DNS регистратора
   (Beget: `ns1.beget.com`, `ns2.beget.com`).
2. Создать записи для GitHub Pages — у apex обязательны **4 A-записи**, ALIAS не нужен:
   ```
   A      @    185.199.108.153
   A      @    185.199.109.153
   A      @    185.199.110.153
   A      @    185.199.111.153
   CNAME  www  weebx.github.io
   ```
3. Перенести MX (`mx1`/`mx2.beget.com`) и TXT (верификации + `_dmarc`), иначе отвалится
   почта и слетят подтверждения в поисковиках.
4. `api`, `dev`, `mail` не переносить — они вели на VPS; `api`/`dev` после восстановления
   вернёшь.
5. Проверка: `dig +short NS weeb-x.com` → NS регистратора,
   `dig +short weeb-x.com` → `185.199.108-111.153`.

Смена NS «вступает в силу» медленнее правки записи: TTL зоны 300 с, но резолверы и
кэш провайдеров могут держать старые NS до нескольких часов. Поэтому, если доступ к
Cloudflare реально можно восстановить (письма «Cloudflare» на почту, автор прошлой
настройки) — это быстрее: там меняется одна запись.

## 3. Восстановление

1. VPS подняли, сайт в Coolify работает (проверь сам).
2. DNS (там, где переключал — Cloudflare или DNS регистратора): удали CNAME
   `@ → weebx.github.io` и 4 A-записи на IP GitHub, верни сохранённые в §2.1 записи
   (`A @ → 109.68.171.140`, `CNAME www → weeb-x.com`).
3. Когда DNS снова смотрит на VPS — обычный сайт и ярус-1 (nginx-заглушка)
   работают сами, Pages можно больше не трогать.

## 4. Синхронизация с основной заглушкой

Единственный источник правды — `fallback-page/html/maintenance.html`. Поменял
тексты/стиль/ссылки там → пересобери копию:

```bash
cd fallback-page/pages && node build-pages.cjs
```

и запушь обе версии (репо сервиса + Pages-репо). Скрипт не даёт рассинхронизироваться:
он падает, если правки не применились или пути не конвертировались.

## 5. Лимиты

- Включение/выключение — руками в DNS (5 минут, нужно достать до Cloudflare из любого места).
  Авто-фейловер не делаем сознательно: DNS-автоматика превращает «резерв» в новый
  единственный источник правды.
- GitHub Pages не умеет `503 + Retry-After` (он всегда отдаёт 200), поэтому здесь нет
  SEO-магии яруса-1, но стоит `noindex, nofollow` — поисковик просто не
  индексирует аварийную страницу.
- Полностью автоматический фейловер без рук — это уже Cloudflare Worker на своём
  домене; отдельная история и не в этом объёме.
