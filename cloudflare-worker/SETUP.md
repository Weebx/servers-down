# Автоматическое переключение заглушки (Cloudflare Cron Worker)

Облачный бот для **Cloudflare Workers**, который работает 24/7 бесплатно и автоматически переключает корневую DNS-запись на резервную страницу GitHub Pages при выключении основного сервера — и сам возвращает трафик обратно при его включении.

## Безопасность

- **В репозитории не хранятся IP-адреса, домены, токены и секреты** — все они задаются как зашифрованные **Secret** внутри панели Cloudflare и недоступны снаружи.
- **Закрытый внешний URL:** любые запросы к `*.workers.dev` без твоего пароля `ADMIN_SECRET` получают пустой `404 Not Found` — посторонние не узнают ни чей это воркер, ни жив ли сервер.
- **Бережный режим:** проверка идёт по умолчанию раз в **3 минуты** (`*/3 * * * *`) лёгким HTTP `HEAD`-запросом на `PROBE_URL`. TCP-подключение к порту `443` остаётся запасным режимом и обнаруживает только отказ сервера/порта, но не остановку приложения за работающим прокси.
- **Защита остальных записей:** поддомены, почта (`MX`) и подтверждения (`TXT`) никогда не изменяются.

## Быстрая настройка в панели Cloudflare (5 минут)

### 1. Выпусти ограниченный API-токен DNS
1. Открой в Cloudflare: **Profile** → **API Tokens** → **Create Token**.
2. Выбери шаблон **Edit zone DNS** (**Use template**).
3. В **Zone Resources** укажи `Include` → `Specific zone` → выбери только свой домен (так токен имеет доступ ровно к одной зоне).
4. Нажми **Continue to summary** → **Create Token** и скопируй ключ.

### 2. Создай Worker
1. Открой **Compute (Workers & Pages)** → **Create** → **Start with Hello World!**.
2. Задай любое нейтральное случайное имя (например, `ops-health-8f3a`) → **Deploy**.
3. Нажми **Edit code**, вставь содержимое [`worker.js`](./worker.js) и нажми **Deploy**.
4. *(Рекомендуется)* Во вкладке **Settings → Domains & Routes** можно вообще отключить маршрут `workers.dev`, если не планируешь открывать `/status` в браузере — Cron-таймер продолжит работать полностью в закрытом режиме.

### 3. Задай приватные секреты
Внутри воркера открой **Settings → Variables and Secrets → + Add** (везде выбирай Type: **Secret**):

| Имя секрета | Что вписать | Обязательно |
| --- | --- | --- |
| `CF_API_TOKEN` | Токен из шага 1 | Да |
| `DOMAIN` | Корневой домен сайта | Да |
| `ORIGIN_IP` | Белый IP основного сервера | Да |
| `FALLBACK_TARGET` | Адрес GitHub Pages (`<организация>.github.io`) | Да |
| `PROBE_URL` | Прямой HTTP(S) health-check приложения на основном сервере | Да, чтобы ловить остановку Docker |
| `ADMIN_SECRET` | Длинный случайный пароль для открытия `/status?secret=...` | По желанию |
| `TG_BOT_TOKEN` | Токен Telegram-бота для уведомлений | По желанию |
| `TG_CHAT_ID` | Твой `chat_id` в Telegram | По желанию |

Нажми **Deploy**, чтобы применить секреты.

### 3.1. Настрой проверку приложения, а не только TCP-порта

Открытый порт `443` не доказывает, что сайт работает: после остановки Docker соединения всё ещё может принимать Coolify, nginx или маршрутизатор. Поэтому для такого сценария нужен `PROBE_URL`.

1. Сделай в **основном приложении** лёгкий endpoint, например `/healthz`, который отвечает `200 OK`, только когда приложение действительно готово. Страница техработ или ответ одного лишь reverse proxy для этого не подходят.
2. Создай отдельную DNS-запись `A health` → `ORIGIN_IP` с **DNS only** и настрой этот hostname в Coolify/nginx (для HTTPS нужен его сертификат). Worker изменяет только `@`, поэтому `health` продолжит вести напрямую на основной сервер даже после включения заглушки.
3. Задай `PROBE_URL=https://health.<твой-домен>/healthz`. Если уже есть отдельный hostname (например, `api`), который всегда смотрит на основной сервер и возвращает `2xx` только у живого приложения, можно использовать его.
4. Проверь endpoint той же командой, которой пользуется Worker:
   ```bash
   curl -I https://health.<твой-домен>/healthz
   ```
   У работающего приложения должен быть ответ `200–299`. При остановленном Docker — таймаут, ошибка соединения или не-`2xx`.

Worker считает здоровым **только `2xx`**: редиректы `3xx`, ответы `4xx` и ошибки прокси `502/503/504` запускают подтверждающие попытки и затем переключение на заглушку.

**Не указывай в `PROBE_URL` корневой домен сайта.** После переключения `@` этот URL будет проверять GitHub Pages, а не основной сервер, из-за чего автоматический возврат трафика станет некорректным.

### 4. Включи расписание (Cron Trigger)
1. В **Settings** воркера открой **Trigger Events / Cron Triggers** → **+ Add Cron Trigger**.
2. Поставь **Every `3` minutes** (`*/3 * * * *`) или **Every `5` minutes** (`*/5 * * * *`) → **Add**.

Переключение не мгновенное: нужно дождаться ближайшего Cron-тика, затем трёх неудачных проверок с двумя паузами по 5 секунд и обновления DNS-кэша. Поэтому «прошла одна минута» ещё ничего не доказывает. `/status` только диагностирует состояние и **не запускает** переключение.

Для немедленной проверки после деплоя вызови защищённый trigger:

```bash
curl -X POST \
  -H "Authorization: Bearer <ADMIN_SECRET>" \
  https://<worker>.workers.dev/trigger
```

При трёх неудачных health-check ответ должен содержать `switched_to_failover` (или `none`, если заглушка уже включена). В `/status` поле `originCheck.probeType` должно быть `http`, а не `tcp`.

## Как на 100% защитить домен от перехвата на GitHub Pages

Чтобы никто посторонний на GitHub никогда не смог привязать твой домен к чужому репозиторию (даже если когда-нибудь удалишь или пересоздашь репо заглушки):
1. Открой настройки своей GitHub-организации → **Settings → Pages** → **Add a domain**.
2. Впиши свой домен и добавь выданную GitHub проверочную запись `TXT _github-pages-challenge-...` в DNS Cloudflare.
3. Нажми **Verify** — после этого GitHub навсегда закрепляет домен исключительно за твоей организацией.
